## 1. 项目背景与目标

### 1.1 场景与问题

日常开发与学习工作中，信息天然分散在三种载体上：**随手记的碎片**（临时想法、待确认事项）、**有层级结构的知识**（方案拆解、知识梳理）、**有时间和优先级属性的任务**（今天做什么、什么先做）。市面上的工具通常只覆盖其中一两类：便签工具不善表达层级，脑图工具不善承载待办，任务工具又很难随手记。

DeskFlow 的目标是把这三类信息放到**同一块无限画布**上：便签用于碎片记录，思维导图节点用于结构化拆解，任务清单与日历用于排期，侧栏用于在多个项目之间切换。

### 1.2 核心取舍：本地优先

在功能规划阶段，项目做了一个明确且贯穿全代码库的取舍——**本地优先（local-first）**：

| 取舍项 | 选择 | 代价 | 换取的东西 |
| --- | --- | --- | --- |
| 数据存放 | 本地 JSON 文件 | 无法多端实时同步 | 数据永远属于用户，直接用文件管理器即可备份、拷贝、迁移 |
| 账号体系 | 不做登录、不做联网 | 无法协作 | 零注册成本，无隐私外泄路径，离线完全可用 |
| 依赖规模 | 运行时依赖仅 PySide6，其余全部为标准库 | 需要自己实现持久化、防抖、原子写入等机制 | 安装体积小、启动快、无第三方库版本冲突风险 |
| 界面技术 | Qt Graphics View 框架（QGraphicsScene / QGraphicsObject） | 需要自行处理图层、命中检测、编辑态切换 | 画布可以自由缩放、平移、分层，图元交互可精细控制 |

这个取舍直接决定了两条设计主线，也是本文档后续章节的重点：

1. **数据安全必须自己做**——没有服务端兜底，任何一次写盘失败都可能让用户丢失整个项目，因此必须有崩溃安全写入与误删恢复机制；
2. **交互层级必须自己做**——画布上混排着便签与导图节点两类图元，谁遮挡谁、谁能生成谁，都需要显式定义规则，而不能依赖 Qt 的默认叠放顺序。

### 1.3 0.1.0 到 0.2.0 的迭代目标

0.1.0 完成了原型验证：画布、便签、导图、任务、侧栏的基本能力可用，但存在三类问题——数据安全机制缺失、若干交互缺陷、工程交付物不完整（无 README / 无启动脚本 / 无截图）。

0.2.0 的迭代目标因此被定义为三条：

| 目标 | 具体交付 |
| --- | --- |
| 数据不再丢 | 崩溃安全写入 + `.bak` 兜底；输入防抖保存 + 20 秒自动保存；误删项目可从 `.trash` 恢复（保留最近 10 个） |
| 交互缺陷清零 | 修复任务筛选错位、画布 `QFrame` 未导入、撤销快捷键与文本框冲突三处缺陷；补齐 z 序分带、导图子树删除、单向生成等交互约束 |
| 可直接展示 | 补齐 README、CHANGELOG、`requirements.txt`、`run.bat`；整理界面截图目录；补充命令行参数 `--data-dir` 与 `--version` |

按 CHANGELOG 的记录，0.2.0 最终落地为：**新增**误删项目恢复、画布空白处双击新建便签、命令行参数、`Open data folder` 入口与工程文件；**修复**3 处缺陷；**改进**画布（缩放/平移/适应内容/网格开关/整理便签/删除撤销栈）、便签（配色/字号/标签/缩放手柄/搜索高亮）、导图（父子节点/贝塞尔连线/重命名/配色/子树删除/自动尺寸）、侧栏（悬停展开/图钉固定/项目切换/日历圆点/任务过滤/优先级/行内编辑）与数据安全机制。

### 1.4 本章要点

- DeskFlow 要解决的是「碎片记录、结构梳理、任务排期」三者割裂的问题，答案是把它们放进同一块画布；
- 「本地优先 + 仅依赖 PySide6」是贯穿全项目的取舍，它把数据安全与图元交互变成必须自研的两条主线；
- 0.2.0 的交付目标是「数据不再丢、交互缺陷清零、可直接展示」，三条目标均有可核对的落地项。

## 2. 系统架构与模块划分

### 2.1 模块清单与职责

DeskFlow 共 11 个功能模块，按职责收进 `deskflow/` 包下的 `core/`（持久化与工具，不依赖 Qt）与 `ui/`（界面）两个子包，`main.py` 作为启动入口保留在项目根目录。模块职责与规模如下：

| 模块 | 职责 | 规模 |
| --- | --- | --- |
| `main.py` | 入口：参数解析、`QApplication` 配置、Fusion 风格与全局 QSS、启动主窗口 | 约 70 行 |
| `deskflow/config.py` | 全项目唯一的常量源：配色、尺寸、字号、z 序区间、超时、上限 | 约 100 行 |
| `deskflow/core/util.py` | 通用工具：ID 生成、时间戳、文件名清洗、任务数据结构归一化 | 约 110 行 |
| `deskflow/core/storage.py` | 崩溃安全 JSON / 文本读写 | 约 60 行 |
| `deskflow/core/data_manager.py` | 项目索引、设置、便签 / 导图 / 任务的持久化、回收站、导出 | 约 470 行 |
| `deskflow/ui/note.py` | 便签图元：绘制、配色、字号、标签胶囊、缩放手柄、行内编辑 | 约 550 行 |
| `deskflow/ui/mindmap.py` | 导图图元：父子节点、贝塞尔连线、重命名、配色、子树删除、自动尺寸 | 约 740 行 |
| `deskflow/ui/canvas.py` | 画布：`QGraphicsScene` / `QGraphicsView`、缩放平移、网格、整理便签、撤销栈 | 约 610 行 |
| `deskflow/ui/sidebar.py` | 抽屉式侧栏：项目切换、任务清单、日历、优先级、行内编辑 | 约 750 行 |
| `deskflow/ui/main_window.py` | 主窗口：菜单栏、工具栏、快捷键、自动保存定时器、窗口几何记忆 | 约 580 行 |
| `deskflow/ui/editor.py` | 便签全屏编辑对话框 | 约 110 行 |

全部模块合计约 4200 行 Python 代码（含包信息文件），运行时依赖仅为 PySide6。

### 2.2 依赖方向：底座无依赖

模块之间保持严格单向依赖，且底座三件套（`config` / `storage` / `util`）不依赖任何业务模块：

```
main.py  (项目根，启动入口)
  └─ deskflow/ui/main_window.py
       ├─ deskflow/ui/canvas.py ──┬─ deskflow/ui/note.py ────┐
       │                           └─ deskflow/ui/mindmap.py ─┤
       ├─ deskflow/ui/sidebar.py ────────────────────────────┤
       └─ deskflow/core/data_manager.py ─────────────────────┤
                                                             ├─ deskflow/core/storage.py
                                                             ├─ deskflow/core/util.py
                                                             └─ deskflow/config.py
```

这样划分带来三个具体收益：

1. **常量集中**：所有可调参数（z 序区间、缩放范围、超时、上限）都在 `deskflow/config.py`，调参不需要在多个文件里搜索魔法数字；
2. **持久化可独立验证**：`deskflow/core/storage.py` 只有 76 行、无业务依赖，可以直接写单元测试覆盖「正常读写 / 文件损坏 / 磁盘不可写」三条路径；
3. **界面与存储解耦**：图元只负责「显示与交互」，`DataManager` 只负责「读写与校验」，两者之间靠普通 Python 数据结构（`dict` / `list`）通信，不传递 Qt 对象。

### 2.3 磁盘布局

运行时数据目录结构如下：

```
data/
├─ projects.json                       项目索引（id / name / 时间戳 / 关联路径）
├─ settings.json                       窗口几何、网格开关、最近项目、缩放
├─ .trash/                             已删除项目（保留最近 10 个）
│   └─ <proj_id>_20260915143012/
└─ projects/
    └─ <proj_id>/
        ├─ notes.json                  便签列表
        ├─ mindmaps.json               导图节点列表
        └─ config.json                 开发工具、任务清单、关联项目路径
```

设计要点有二：

- **索引与内容分离**：`projects.json` 只在新建 / 重命名 / 删除项目时写入，日常编辑便签不会触碰它，减少写放大与损坏面；
- **按项目分目录**：一个项目的全部数据集中在一个目录内，删除 / 恢复 / 整体拷贝都以「移动一个目录」为单位完成，不需要遍历多个文件。

### 2.4 一次编辑的完整流转

以「用户拖动便签并输入文字」为例，一次编辑在系统中的完整路径是：

1. `deskflow/ui/note.py` 的图元接收鼠标事件，更新自身的位置与文本并重绘；
2. 图元发出「内容变化」信号，`deskflow/ui/canvas.py` 汇总当前场景中的便签与导图节点状态；
3. 状态变化触发**输入防抖定时器（600 ms）**，期间持续输入不会反复写盘；
4. 防抖到期或 **20 秒自动保存定时器**触发，`deskflow/ui/main_window.py` 调用 `DataManager.save_notes(...)`；
5. `DataManager` 归一化数据结构后交给 `storage.write_json`；
6. `storage` 先把旧文件复制为 `.bak`，再写入 `.tmp`，`flush` + `os.fsync` 落盘，最后用 `os.replace` 原子替换为目标文件。

这条链路上每一层都只做一件事，因此排查问题时的定位路径非常明确：交互不对找图元、状态不对找画布、数据不对找 `DataManager`、文件坏了找 `storage`。

### 2.5 数据目录的回退判定

应用默认把数据放在项目自身的 `data/` 目录（便于「解压即用、数据随身」）。但若应用被安装到 `C:\Program Files` 这类受保护路径，该目录不可写，因此 `data_manager.resolve_data_root()` 会按顺序探测候选目录：

| 顺序 | 候选目录 | 说明 |
| --- | --- | --- |
| 1 | `<应用目录>/data` | 默认；便携场景下的首选 |
| 2 | `%APPDATA%/DeskFlow/data` | 漫游配置目录（域环境下可跟随用户） |
| 3 | `%LOCALAPPDATA%/DeskFlow/data` | 本机配置目录 |
| 4 | `~/DeskFlow/data` | 用户主目录兜底 |
| 5 | `<应用目录>/data`（回退返回） | 全部不可写时仍返回默认路径，由调用方降级处理 |

可写性判定不是「检查目录是否存在」，而是**实际写入探针文件**（`.write_probe`）并删除——只有真正完成一次读写，才能排除「目录存在但只读」的情况。判定结果在模块导入时计算一次并缓存为 `DEFAULT_DATA_ROOT`，避免每次写盘都做探测。

### 2.6 本章要点

- 10 个模块职责单一，依赖严格单向；`config` / `storage` / `util` 作为无依赖底座，使常量集中、持久化可独立测试；
- 磁盘布局采用「索引与内容分离 + 按项目分目录」，让删除、恢复、迁移都以目录为单位；
- 一次编辑通过「图元 → 画布 → 防抖定时器 → DataManager → storage 原子写」五级流转，每层职责清晰可定位；
- 数据目录回退采用实际写探针而非存在性判断，兼容便携使用与受限安装目录两种场景。

## 3. 核心功能实现细节

### 3.1 图元体系：便签与导图节点

便签与导图节点都是 `QGraphicsObject` 的子类，遵循 Qt Graphics View 框架的三件套约定：

| 方法 | 职责 |
| --- | --- |
| `boundingRect()` | 声明图元占用的矩形区域，决定重绘与命中检测的边界 |
| `shape()` | 返回精确的命中形状（圆角矩形），使点击判定与视觉边界一致 |
| `paint()` | 绘制背景、文本、标签胶囊、选中态与缩放手柄 |

便签的可用视觉参数全部集中在 `deskflow/config.py`，包括 8 组低饱和配色、3 档字号（11 / 13 / 16 pt）、3 档预设尺寸（180×140 / 220×180 / 280×220），以及尺寸上下限（最小 150×110，最大 900×700）。缩放手柄固定在右下角，占用 16 px 的预留条；顶部预留 26 px 的标签条，用于放置标签胶囊。这样安排的目的是让「文本区」永远是纯文本区——标签、手柄、选中框都在预留条内绘制，不与正文争夺空间。

### 3.2 z 序分带：用数值区间固化交互规则

画布上混排着两类图元，如果沿用「谁最后被点击谁在最上层」的默认策略，用户拖动便签时很容易把导图节点整片盖住，且无法通过再次点击恢复层级关系。DeskFlow 的做法是把 z 序划分成互不重叠的三个区间：

| 区间 | 取值范围 | 归属 |
| --- | --- | --- |
| 便签带 | `0.0 – 999.0` | 所有便签 |
| 导图带 | `1000.0 – 1999.0` | 所有导图节点及其连线 |
| 幽灵带 | `2000.0` | 导图节点的「添加槽」（Ghost），必须始终可点击 |

含义是：便签之间的置顶操作只在 0–999 内递增，导图节点之间的层级调整只在 1000–1999 内递增。**两个区间互不相交，因此便签永远不可能遮挡导图节点，无论用户点击多少次。** 这条规则不是靠事件回调中的条件判断拼出来的，而是被固化为一组常量——把「交互不变量」写成数值约束，是避免这类缺陷反复出现的最省事做法。

### 3.3 思维导图：父子结构、子树删除与单向生成

导图节点通过 `parent_id` 组成森林结构（根节点的 `parent_id` 为空），每条父子关系在场景中对应一条平滑贝塞尔连线。三项关键交互如下：

1. **子树删除**：删除节点时递归收集全部后代并一并移除，同时清理对应的连线图元。若不递归，孤儿子节点会因为父节点消失而成为无法访问的悬空数据。
2. **自动尺寸**：节点尺寸随文本长度自动扩展，避免长文本被裁切。
3. **单向生成**：节点悬停时出现的「添加槽」（Ghost）只向**单一方向**生成子节点，而不是左右两侧都提供添加入口。这是 0.2.0 修复的一处交互缺陷——双向生成会让父子关系在视觉上左右混排，节点增多后连线交叉严重，用户也无法预期「新节点会出现在哪一侧」。约束为单向之后，新增节点的位置完全可预期。

对应的验证材料是 `docs/screenshots/test02_right_direction.png` 与 `test03_hover_delete_button.png`、`test04_rightclick_delete_menu.png`，分别记录了「新增节点方向」「悬停删除按钮」「右键删除菜单」三个交互点。

### 3.4 撤销、防抖保存与自动保存

数据安全与「不卡手」这两件事在实现上存在天然冲突：保存越频繁越安全，但写盘会阻塞界面。DeskFlow 用三层机制做平衡：

| 机制 | 参数 | 作用 |
| --- | --- | --- |
| 输入防抖 | 600 ms | 连续输入期间只在停顿后触发一次保存，避免每敲一个字就写盘 |
| 周期自动保存 | 20 000 ms | 即使长时间没有触发防抖（例如只拖动、不输入），也按周期兜底落盘 |
| 关闭时保存 | 窗口关闭事件 | 保存窗口几何与当前界面偏好到 `settings.json` |

撤销方面，画布维护一个**上限为 30 步**的撤销栈，覆盖便签删除、复制等内容变更（`Delete` 删除前会先询问）。撤销快捷键被设定为 `Ctrl+Shift+Z` 而非 `Ctrl+Z`，原因是文本框内的 `Ctrl+Z` 需要保留给文本自身的撤销——如果两者共用同一快捷键，用户在编辑便签文字时按 `Ctrl+Z` 会同时触发「文本撤销」与「画布撤销」，产生难以理解的结果。这是 0.2.0 修复的第三处缺陷，本质上是一次**快捷键作用域冲突**。

### 3.5 画布交互与检索

| 能力 | 实现要点 |
| --- | --- |
| 缩放 | 缩放系数限制在 0.4 – 2.5 之间，单次步进 1.15，避免缩放到不可用比例 |
| 平移 / 适应内容 | 画布最小尺寸 2400 px，配合边距保证图元拖出视口后仍可找回 |
| 网格 | 可开关，网格线使用两档浅色（普通格 / 强格）区分主次 |
| 整理便签 | 一键把散落便签按网格对齐排布，不改变层级与内容 |
| 全局搜索 | `Ctrl+F` 覆盖便签正文、标签与导图节点文本三类对象 |
| 命中反馈 | 搜索命中的便签高亮显示；按标签过滤时，非目标便签做淡化处理而非隐藏，保留空间记忆 |

搜索与过滤的区别是有意设计的：**搜索用于「找到」（需要强提示），过滤用于「聚焦」（需要保留上下文）**。如果过滤直接隐藏不匹配的便签，布局会瞬间重排，用户反而会失去对内容的方位感。

### 3.6 本章要点

- 图元遵循 `boundingRect` / `shape` / `paint` 三件套，视觉参数（配色、字号、尺寸、预留条）全部集中在 `deskflow/config.py`；
- z 序分带把「便签不遮挡导图」固化为数值不变量，而非运行时条件判断；
- 导图的子树删除保证数据无悬空，单向生成保证新增节点位置可预期；
- 撤销（30 步、`Ctrl+Shift+Z`）、防抖（600 ms）与自动保存（20 s）三层机制共同覆盖「不卡手」与「不丢数据」；
- 搜索强调提示、过滤保留上下文，两者的行为差异是刻意的。

## 4. 工程难题与解决方案

### 4.1 难题一：如何保证「任何一次写盘失败都不丢数据」

| 环节 | 内容 |
| --- | --- |
| 现象 | 直接以「打开文件 → 覆盖写入」的方式保存 JSON 时，进程崩溃、断电或磁盘写满都可能留下一个**半截文件**——语法不完整，下次启动直接读取失败，整个项目数据报废 |
| 原因 | 覆盖写不是原子操作：新内容写入到一半时，旧内容已经被截断 |
| 方案 | 三步式崩溃安全写入：①把现有文件复制为 `<name>.json.bak`；②写入临时文件 `<name>.json.tmp`，`flush()` 后调用 `os.fsync()` 强制落盘；③用 `os.replace()` 原子替换目标文件 |
| 验证 | 读取侧做同样的三层降级：优先读主文件，解析失败则回退读 `.bak`，再失败才返回默认值；所有异常（`JSONDecodeError` / `OSError` / `UnicodeDecodeError`）都被捕获，不让一个坏文件阻断启动 |

这里的三个动作缺一不可，各自对应一类失败：

- **`.bak` 备份**：解决「新内容写坏了、旧内容也没了」；
- **`fsync`**：解决「系统缓冲区还没落盘就断电」——`flush()` 只把数据交给操作系统，`fsync()` 才要求真正写入磁盘；
- **`os.replace`**：解决「写到一半被杀」。在主流文件系统上重命名是原子操作，因此目标文件要么是完整的旧版本，要么是完整的新版本。

写入函数返回布尔值而不抛异常，并被设计为**尽力而为**：备份失败（例如磁盘只读）不会中断主写入流程，避免「为了安全反而写不进去」。上层调用方据此决定是否提示用户。

### 4.2 难题二：误删可恢复，且回收站不无限膨胀

删项目是不可逆的高风险操作，DeskFlow 的解法是「**不物理删除，只移动**」：

| 环节 | 内容 |
| --- | --- |
| 现象 | 用户误删项目后希望找回 |
| 方案 | `delete_project()` 优先把项目目录移动（`shutil.move`）到 `.trash/`，目录名携带项目 id 与删除时间戳（`<proj_id>_20260915143012`），并同步从 `projects.json` 索引中移除 |
| 膨胀控制 | 每次移入回收站后调用 `_prune_trash(keep=10)`，按修改时间倒序保留最近 10 个，更早的才真正删除 |
| 恢复路径 | 菜单 `File ▸ Restore deleted project…` 列出回收站内容（含删除时间、按时间倒序），用户选择后把目录移回 `projects/` 并重新登记索引 |
| 边界处理 | 若恢复时目标 id 已被占用（或目录已存在），自动追加随机后缀生成新 id，避免覆盖现有项目 |

设计上有两点值得说明：

1. **移动而非复制**：删除与恢复都是同一文件系统内的重命名操作，代价接近零，不需要考虑大目录拷贝耗时；
2. **索引与目录分离更新**：先更新索引再移动目录，移动失败时也有明确的错误分支（回退为直接删除），不会出现「索引说删了、目录还在」的中间状态长期存在。

`.trash` 保留 10 个的上限是一个显式取舍：**用「有限的后悔窗口」换「磁盘不失控」**。对于个人项目数据（量级为几十 KB 到几 MB），10 个项目的回收站容量对磁盘几乎无影响，足以覆盖绝大多数误删场景。

### 4.3 难题三：受限安装目录下的可写性判定

| 环节 | 内容 |
| --- | --- |
| 现象 | 应用默认把数据放在自身目录下，但若被安装到 `C:\Program Files` 之类的受保护路径，写入会失败 |
| 原因 | 「目录是否存在」不能代表「目录是否可写」——权限、只读属性、磁盘配额都可能导致写入失败 |
| 方案 | 用**实际写探针**判定：在候选目录写入 `.write_probe` 文件后立即删除，任一步骤抛 `OSError` 即判定不可写，并按「应用目录 → `%APPDATA%` → `%LOCALAPPDATA%` → 用户主目录」的顺序探测；结果在模块导入时算一次并缓存 |
| 验证 | 全部候选都不可写时仍返回默认路径，由调用方降级处理，保证程序不会因为找不到可写目录而直接崩溃 |

这个判定点的意义在于：**「便携使用」与「受限安装」是两个必须同时支持的场景**，而它们对数据目录的要求相反——前者要求数据跟着程序走，后者要求数据必须离开程序目录。

### 4.4 难题四：三处交互缺陷的根因与修复

0.2.0 修复的三处缺陷，表面无关，根因却指向同一类问题：**隐式假设没有落到显式约束**。

| 缺陷 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 任务筛选错位 | 筛选后操作某一行，被修改的却是另一条任务 | 行与数据之间靠**列表索引**对应；筛选后显示的行序号与原始列表下标错位 | 每一行显式绑定自己的任务 id，所有操作按 id 查找而非按下标 |
| 画布 `QFrame` 未导入 | 绘制失败 | 依赖隐式导入（在其它模块里被间接引入），一旦导入链变化即崩溃 | 补齐显式导入，并在文件内保持导入自足 |
| 撤销快捷键冲突 | 在文本框内按 `Ctrl+Z`，同时触发文本撤销与画布撤销 | 快捷键作用域重叠：同一个组合键被两个层级同时消费 | 撤销快捷键改为 `Ctrl+Shift+Z`，把 `Ctrl+Z` 留给文本编辑 |

三条修复背后可以提炼出一条通用检查项：**凡是「用位置表示身份」的地方都要警惕**（索引 → id），**凡是「依赖环境隐式提供」的东西都要显式声明**（导入、快捷键作用域）。

### 4.5 本章要点

- 崩溃安全写入由「`.bak` 备份 + `fsync` + 原子替换」三步构成，分别对应三类真实失败模式，配套的读取降级保证坏文件不阻断启动；
- 误删恢复用「移动 + 时间戳命名 + 保留最近 10 个」实现可恢复与不膨胀的平衡；
- 数据目录的可写性必须通过实际写探针判定，才能同时支持便携使用与受限安装；
- 三处交互缺陷的根因统一为「隐式假设未显式化」，对应两条可复用的检查项：位置不表示身份、依赖必须显式声明。

## 6. 可扩展方向

DeskFlow 的架构（无依赖底座 + 单向依赖 + 界面与存储解耦）为后续演进留出了明确的空间。以下按「质量 → 性能 → 功能 → 协作」的顺序展开。

### 6.1 测试与质量保障

| 方向 | 现状 | 具体工作 |
| --- | --- | --- |
| 纯逻辑单元测试 | 无测试 | 优先覆盖三块最适合：`deskflow/core/storage.py`（正常写入 / 文件损坏回退 / 目录不可写）、`deskflow/core/util.py`（任务结构与时间处理）、`deskflow/core/data_manager.py`（索引增删、回收站 FIFO 淘汰、id 冲突恢复） |
| 界面自动化 | 无 | 引入 `pytest-qt`（或 Qt 自带的 `QTest`）做关键路径的自动化：新建便签 → 编辑 → 撤销 → 保存 → 重启后校验数据 |
| 崩溃安全回归 | 有机制、无自动化验证 | 用「写入过程中注入异常」的方式验证 `.bak` 兜底路径真的被走到 |
| 截图回归 | 有 6 张交互验证截图 | 把截图基准纳入检查流程，交互改动后对比截图差异 |
| CI | 无 | 在 Windows 环境的 CI 上跑「编译检查 + 单元测试 + offscreen 启动冒烟」 |

**为什么把测试排在第一位。** 本项目最核心的卖点是「数据不会丢」，而这类机制的失效是低频且致命的——它不会在正常使用中暴露，只会在真正需要它的那一刻暴露。因此它是明确的最高优先级。

### 6.2 数据层演进

| 方向 | 触发条件 | 方案 |
| --- | --- | --- |
| JSON → SQLite | 单个项目便签 / 任务进入数千条量级，或需要「按条件查询」而非「全量加载」 | 用 SQLite 提供事务与并发保护，保留 JSON 导出能力作为兼容出口 |
| 增量写入 | 大项目下保存耗时变得可感知 | 现在写入以「项目」为粒度整体序列化；可改为按实体记录差异，只写变化部分 |
| 数据格式版本号 | 未来字段结构发生变化 | 在 JSON 顶层加入 `schema_version`，读取时按版本做迁移，避免老数据无法打开 |
| 校验与自愈 | 主文件损坏但 `.bak` 也存在问题时 | 增加结构校验（字段类型白名单），损坏字段降级为默认值并记录日志 |

### 6.3 功能扩展

| 方向 | 说明 |
| --- | --- |
| 标签体系增强 | 目前标签配色由预置映射给出；可支持自定义标签、标签树与跨项目标签视图 |
| 任务能力 | 重复任务规则、子任务拆解、按项目聚合的今日视图 |

| 画布增强 | 分组框选、对齐吸附、导图自动树形布局 |

### 6.4 性能演进

| 方向 | 现状 | 方案 |
| --- | --- | --- |
| 大量图元的绘制 | 图元数量增加后重绘开销上升 | 视口裁剪（只绘制可见区域）+ `QGraphicsItem` 缓存模式（`DeviceCoordinateCache`） |

### 6.5 协作与同步（谨慎推进）

本地优先是项目的核心取舍，因此同步能力的方向不是「加一个云账号」，而是**保持文件格式的开放与可合并**：

| 方向 | 思路 |
| --- | --- |
| 文件级同步 | 数据是纯 JSON + 按项目分目录，天然适合用网盘 / Syncthing 做文件级同步 |
| 冲突处理 | 设计「按实体 id 合并、冲突保留双份」的合并策略，避免同步导致丢数据 |
| 导出互通 | 增强 Markdown / JSON 导出，便于迁移到其他工具，降低「用久了出不去」的顾虑 |

### 6.6 优先级建议
